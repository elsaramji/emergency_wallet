Product Vision & Mission

A comprehensive overview of why Emergency Wallet was built, what problems it solves, and its core philosophy.

The Core Philosophy

Emergency Wallet is built around a distinct behavior design concept: "friction on withdrawal, ease on deposit." Ordinary savings apps treat all budgets equally; we implement active protective barriers around emergency savings to prevent impulsive raiding.

The Core Problem

Most people fail to maintain an emergency fund not due to lack of income, but because standard financial tools lack behavioral limits. Regular wallets keep emergency reserves instantly accessible. When a non-emergency purchase arises, the funds are raided and rarely replenished.

The Solution

  • Salary Auto-Save Target: 20% of salary is automatically routed to a locked Emergency Wallet.
  • Withdrawal Friction: Withdrawing from the Emergency Wallet triggers an intentional "Emergency Lock" mechanism forcing users to explicitly declare a crisis.
  • Consolidated Liquidity: Displays a single unified balance across Cash, Visa cards, and Smart Wallets.

Success Criteria

Objective Target Metric Measurement
Market Validation ≥ 1,000 active users Within 60 days of release
Feature Engagement ≥ 70% of salaried users Enable the Auto-Save Emergency Wallet rules
User Retention ≥ 40% 30-day cohort retention rate
Real-world Utility ≥ 1 Cashout event Logged within 30 days

Quick Start & Setup

Get the project up and running on your local machine for active development.

Prerequisites

Ensure you have the following installed on your machine:

  • Flutter SDK: Version stable (Dart 3.x)
  • Git (for source control)
  • Firebase CLI: Needed to manage and deploy database security rules

Installation Instructions

Run these commands in your preferred terminal:

# Clone the repository
git clone https://github.com/elsaramji/emergency_wallet.git

# Navigate to project directory
cd emergency_wallet

# Retrieve Flutter packages
flutter pub get

# Launch on a connected device
flutter run
Firebase Configuration Required

Running the application with live sync requires a Firebase project configured. Run flutterfire configure to update local configurations, and ensure Cloud Firestore is enabled in your Firebase console.

Clean Architecture

The codebase is designed using Feature-based Clean Architecture, separating responsibilities into three distinct layers.

Dependency Flow Rule

Dependencies must flow strictly inward: Presentation → Domain and Data → Domain. The Domain layer must remain pure Dart, with absolutely no references to UI frameworks, Flutter packages, or remote database modules.

Project Folder Structure

lib/ ├── core/ # Global utilities, DI, router, app themes, localization └── features/ # Feature directories (e.g., auth, dashboard, insights) └── [feature_name]/ ├── domain/ # Entities, Repository Contracts, Use Cases (Pure Dart) ├── data/ # Repos implementations, Data Sources, Models, Mappers └── presentation/ # Cubit/States, Views, Widgets (Flutter UI)

Layer Responsibilities

1. Domain Layer

  • Entities: Core business models (e.g., UserEntity, TransactionEntity).
  • Repository Interfaces: Abstract contracts defining data operations.
  • Use Cases: Application-specific business rules.
  • Errors: Enforces the Either/Result pattern using a base Failure class defined in core/errors/failures.dart to avoid throwing raw exceptions to the UI.

2. Data Layer

  • Data Sources: Handles API requests, Firestore queries (RemoteDataSource), or local device storage (LocalDataSource).
  • DTOs / Models: Implements JSON serialization/deserialization (e.g., TransactionModel.fromJson()).
  • Mappers: Helper extensions translating DTOs to Domain Entities (e.g., model.toEntity()).

3. Presentation Layer

  • Views: Core screens (e.g., DashboardView).
  • Widgets: Small, reusable UI elements.
  • State Management: Governed exclusively by BLoC Cubits.
  • State Pattern: Follows a standard lifecycle: Initial → Loading → Success or Failure (carrying a Failure object).

Dependency Injection & Routing

  • DI Service Locator: Powered by get_it and injectable. Service classes, datasources, and repositories are marked with @injectable, @lazySingleton, or @singleton. Run build_runner to regenerate injection configs.
  • Routing: Managed via a single standalone GoRouter instance registered globally. Route path constants are declared in core/router/app_routes.dart.

Firestore Database Schema

The database schema is built around data integrity, real-time sync, and monthly aggregation constraints.

Collection Tree

Firestore Root └── users/ └── {uid}/ # User document ├── profile/ # Subcollection: User profile info │ └── data # Single document ├── strategy/ # Subcollection: Salary, auto-save status │ └── data # Single document ├── money/ # Subcollection: Multi-wallet balances │ └── data # Single document ├── transactions/ # Subcollection: Flat list for recent activity │ ├── {transactionId} │ └── ... └── transactionHistory/ # Subcollection: Aggregated monthly buckets └── {YYYY-MM}/ # e.g., "2026-08" └── entries/ # Subcollection: Transactions of that month

Design Patterns

Dual-Write Batch Writes

To avoid balance mismatch, a transaction log and the user's running balance are written in a single atomic batch write. The write either succeeds completely or fails completely, preventing corrupted records.

Monthly Bucketing

Queries for transactions are divided month-by-month in transactionHistory/{YYYY-MM}. This prevents the database from reading thousands of flat records when loading historical logs, dramatically saving Firestore reads and improving speed.

Emergency Wallet Lock Rule

Lock Constraint

Inside users/{uid}/money/data, the field emergencyWalletLocked is set to true whenever the computed totalBalance <= 50 EGP. While locked, Cloud Security Rules block any outgoing transaction targeting the Emergency Wallet.

Schema Details

users/{uid}/money/data (Balances)

Field Type Description
cashAmount number Physical Cash balance (Primary priority)
visaAmount number Bank card liquidity
phoneWalletAmount number Mobile cash wallets (Vodafone Cash, Fawry)
emergencyWalletAmount number Protected emergency savings
emergencyWalletLocked boolean Blocks withdrawals when true
totalBalance number Calculated sum of all channels

The design system is optimized for readability, trust, and localization within the Egyptian & MENA fintech space.

MENA Localization Rules

  • Arabic Mirroring: Layouts, swipe directions, and page slide animations automatically reverse in RTL mode.
  • Numbers rule LTR: Numbers are universally read from left-to-right in the Middle East, so currency and phone numbers remain LTR in both LTR/RTL viewports.
  • Cash First: Egyptians operate cash-first. The Cash Wallet card takes the top visual priority on the Dashboard.
  • Warm Copy Tone: Egyptian-Arabic translations use warm, colloquial finance terms, completely avoiding formal modern standard Arabic (Fusha) to build trust.

Developer Guidelines & CLI

Rules and commands that developers must strictly adhere to when modifying the Flutter codebase.

General Rules

  • Responsive Sizes: Always use flutter_screenutil extensions for dimensions (e.g. .h, .w, .sp, .r). Avoid raw pixel values.
  • Localization: Never hardcode user-facing strings. Add translation keys inside lib/core/localization/l10n/app_en.arb and app_ar.arb, and compile the code to access them via context.local.keyName.
  • Themes: Access all colors and text styles from the context theme (e.g. context.colorScheme.primary, context.textTheme.bodyLarge). Direct references to raw Color variables in view files is strictly prohibited.

Useful Developer Commands

Command Task
flutter pub get Install / update dependencies
flutter pub run build_runner build --delete-conflicting-outputs Generate DI locator & model configurations
flutter gen-l10n Regenerate localization translation files
flutter analyze Scan code for linter errors
flutter test Run local unit and widget tests
